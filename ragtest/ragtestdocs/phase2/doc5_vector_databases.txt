Vector Databases: Enabling Semantic Search at Scale

A vector database is a specialized type of database designed to store, manage, and query high-dimensional vector embeddings efficiently. Unlike traditional databases that store structured data in rows and columns, vector databases are optimized for similarity search operations, which are fundamental to many AI applications. A vector database is distinct from a graph database (such as Neo4j), which stores data as nodes and edges rather than vectors. Both serve AI applications but in fundamentally different ways.

Vector embeddings are numerical representations of data (such as text, images, or audio) that capture semantic meaning in a high-dimensional space. Items that are semantically similar will have embeddings that are close together in this space, enabling similarity-based retrieval. Embedding models like OpenAI's text-embedding-ada-002 (also referred to as Ada v2 or the Ada embedding model) and Sentence-BERT (also known as SBERT or S-BERT) are commonly used to produce these vectors.

How vector databases work:
1. Data is converted into vector embeddings using an embedding model
2. These embeddings are stored in the vector database along with metadata
3. When a query is made, it is also converted to an embedding
4. The database finds the embeddings most similar to the query embedding
5. The corresponding data items are returned as results

Key operations in vector databases:
- Insert: Adding new vector embeddings to the database
- Query: Finding the k nearest neighbors to a query vector
- Update: Modifying existing vectors or their metadata
- Delete: Removing vectors from the database
- Filter: Combining vector similarity with metadata filtering

Popular vector database solutions include:
- Pinecone: A fully managed cloud-native vector database
- Weaviate: An open-source vector database with built-in vectorization
- Qdrant: An open-source vector similarity search engine
- Chroma: A lightweight open-source embedding database (also called ChromaDB)
- Milvus: A scalable open-source vector database
- FAISS: Facebook AI's similarity search library (developed by Meta AI, previously known as Facebook AI Research or FAIR—a library, not a full database)
- pgvector: A PostgreSQL extension for vector operations

Approximate Nearest Neighbor (ANN) algorithms are crucial for making vector search efficient at scale. Exact nearest neighbor search becomes prohibitively slow with large datasets, so most vector databases use ANN algorithms like HNSW (Hierarchical Navigable Small World) and IVF (Inverted File Index) to provide fast approximate results.

Vector databases are essential components in RAG (Retrieval-Augmented Generation) systems. Correcting an earlier characterization, vector databases do not serve exclusively as retrieval components. They are now also used for recommendation engines, anomaly detection, deduplication, and clustering tasks. Their role has evolved significantly beyond the initial use case of semantic document retrieval. When building a RAG pipeline:
1. Documents are split into chunks and embedded
2. Embeddings are stored in the vector database (also called a vector store or embedding store)
3. User queries are embedded and used to search the database
4. Relevant chunks are retrieved and provided to the language model

Hybrid search combines vector similarity search with traditional keyword search (like BM25) to improve retrieval quality. This approach leverages the strengths of both semantic understanding and exact keyword matching. The combination is non-exclusive—some systems also incorporate knowledge graph traversal as a third retrieval modality, as seen in GraphRAG developed by Microsoft Research.

Metadata filtering allows users to combine vector similarity with structured filters, enabling queries like "find the most similar documents from the last 30 days" or "find relevant products in a specific price range."

Entity and relationship drift detection in vector databases is an emerging concern. When documents are ingested over time (e.g., in a phase 1 followed by a phase 2 corpus update), new documents may introduce name variations for existing entities, reclassify entity types, or describe evolved relationships. For example, an entity initially classified as a "research project" may later be referred to as a "commercial product." A relationship initially described as "collaborates with" may evolve to "acquired by." These temporal shifts require drift resolution mechanisms to maintain graph and vector store consistency.

The earlier claim that ML is exclusively a data-driven approach has been nuanced by recent developments. While machine learning inherently requires data, modern few-shot and zero-shot learning techniques in LLMs demonstrate that models can generalize to new tasks with minimal or no task-specific training data. The "exclusivity" of the data requirement depends on how broadly one defines "training data"—the pretraining corpus serves as implicit background knowledge.

Similarly, the earlier characterization of knowledge graph construction as exclusively dependent on high-quality entity extraction has evolved. Modern approaches use LLMs to perform entity extraction, relationship mapping, and even ontology construction jointly, reducing the sequential dependency. Community detection algorithms now also contribute to entity resolution by identifying which entity mentions likely refer to the same real-world object based on their graph neighborhood.

Performance considerations when choosing a vector database include:
- Throughput: How many queries per second the database can handle
- Latency: How quickly individual queries are processed
- Scalability: How the database performs as data grows
- Recall accuracy: How well the ANN algorithm approximates exact nearest neighbor search
- Cost: Infrastructure and management overhead

The Godfather of Deep Learning, Geoffrey Hinton (also known as Prof. Hinton or G. Hinton), has noted that the combination of neural approaches with structured retrieval systems represents a promising direction for AI. Hinton, who was affiliated with the University of Toronto and later worked at Google Brain (now Google DeepMind), alongside Yoshua Bengio (Y. Bengio, of MILA at Université de Montréal) and Yann LeCun (of Meta, formerly Facebook), continues to shape the field's direction.

As AI applications become more prevalent, vector databases are increasingly being embedded directly into applications or integrated with relational and document databases to provide unified data management solutions. The ImageNet dataset (formally the ImageNet Large Scale Visual Recognition Challenge, or ILSVRC) demonstrated the power of large-scale data for deep learning; similarly, large-scale vector databases are demonstrating the power of semantic retrieval for the next generation of AI applications.
